no-cache 不是「不要快取」：HTTP 快取標頭的實際語意

2026 年 9 月 13 日 · 約 10 分鐘

`Cache-Control: no-cache` 這個名字取得很糟。它不是「不要快取」——它允許快取儲存這份回應，只是要求每次使用前先向源站確認還新不新。真正禁止儲存的指令叫 `no-store`。這個命名造成的誤解有實際後果：想保護敏感資料的人用了 no-cache，資料仍然被寫到磁碟；想避免風險的人一律用 no-store，效能整個賠進去。

六個指令與它們實際的意思

HTTP 快取的規範是 RFC 9111，裡面每個指令的語意都有明確定義。問題在於其中幾個的名字與直覺不符，而多數人是從別人的設定檔複製過來、沒查過規範。

最關鍵的區分是儲存與使用：快取可以儲存一份回應，但在使用它之前可能需要先驗證。`no-cache` 管的是後者，`no-store` 管的是前者——名字容易混淆，行為完全不同。

下表列出六個最常用的指令。第一列就是那個被誤解得最嚴重的。

這個誤解造成的三種實際後果

名稱誤導不只是學術問題，以下三種都會實際發生：

  1. 用 no-cache 保護敏感資料是無效的 想讓帳單頁面、個人資料不被留下痕跡，設了 `no-cache` 就以為安全了。但依規範，快取仍然可以把整份回應寫進磁碟，只是下次使用前要驗證。共用電腦上的瀏覽器快取、企業的代理伺服器，都可能留著那份內容。要真正不留存，必須用 `no-store`。
  2. 一律用 no-store 會賠掉效能 知道 no-store 比較保險之後，有些人乾脆全站都設。結果是每一次請求都要完整回源，CDN 形同虛設，靜態資源也不再被瀏覽器重用。正確做法是分清楚哪些回應真的含個人資料——通常只有登入後的動態頁面——其餘照常快取。
  3. 不知道 s-maxage 導致 CDN 與瀏覽器綁在一起 `max-age` 同時作用於瀏覽器與 CDN，所以想讓 CDN 快取久一點、瀏覽器短一點，用單一指令做不到。`s-maxage` 就是為此存在：它只對共享快取生效，而且會覆蓋 max-age。設定 `max-age=60, s-maxage=86400` 的意思是瀏覽器一分鐘、CDN 一天——這是 CDN 調校最基本也最常被忽略的工具。

Vary：決定快取鍵的那個標頭

快取預設以網址作為鍵。但如果同一個網址會依請求標頭回傳不同內容（例如依 `Accept-Encoding` 給壓縮或未壓縮版本），快取必須知道這件事，否則會把壓縮版回給不支援的客戶端。`Vary` 就是用來宣告「這些請求標頭會影響回應內容」。

依規範，快取在使用已儲存的回應之前，`Vary` 列出的每一個請求標頭都必須與當初那次請求相符，否則不得直接使用。所以 Vary 列得越多，快取命中率越低——每一個被列入的標頭都會讓快取鍵再細分一次。

最常見的災難是 `Vary: User-Agent`。User-Agent 字串的變體數以萬計，等於為每一種瀏覽器版本各存一份——實際效果接近完全停用快取，但設定看起來一切正常，只是命中率莫名其妙地低。相對地 `Vary: Accept-Encoding` 是合理且必要的，因為它的取值只有少數幾種。

如果您的 CDN 命中率低得不合理，`Vary` 是第一個該檢查的地方。這個問題不會產生任何錯誤訊息，只會安靜地讓每一次請求都回源。

過期之後：ETag 與條件式請求

快取過期不代表內容變了。這時候快取可以發出條件式請求：帶上先前拿到的 `ETag`（內容指紋）或 `Last-Modified`（修改時間），問源站「還是這一份嗎？」。如果沒變，源站回 `304 Not Modified`，只有標頭沒有內容。

這就是 `no-cache` 真正的用途——它強制每次都走這個驗證流程，但保留了 304 的快速路徑。對於「必須是最新、但通常不會變」的內容（例如 HTML 首頁），`no-cache` 加上 ETag 的組合，比起 `no-store` 每次完整傳輸有效率得多，同時仍保證使用者不會看到舊內容。

三個層次的設定

實務上可以依內容性質分成三類處理：

一、帶版本或指紋的靜態資源

檔名含雜湊的 JS、CSS、圖片，內容永遠不會變（變了就是新檔名）。這類可以設很長的 max-age 並加上 `immutable`，讓瀏覽器連驗證都省下。這是效能收益最大、風險最低的一類。

二、會變動但不敏感的內容

HTML 頁面、API 的公開回應。適合 `no-cache` 或短的 max-age 搭配 ETag——確保拿到最新版本，但不變時只付出一次 304 的成本。若想讓 CDN 擋掉大部分流量，再用 s-maxage 拉長邊緣的快取時間。

三、含個人資料的回應

登入後的頁面、帳務資訊、任何帶身分的內容。這類要用 `no-store`，而不是 `no-cache`。如果只是不想讓 CDN 存、但瀏覽器可以存，那是 `private` 的用途。三者不要混用。

排查快取問題時該先確認的三件事

命中率不如預期或內容沒更新時，這三項最常是原因：

  1. 確認 Vary 列了什麼 用瀏覽器開發者工具或 curl 看實際回應標頭。若列了 User-Agent 或 Cookie 之類取值極多的標頭，快取幾乎不可能命中，而這不會有任何錯誤提示。
  2. 確認 s-maxage 與 max-age 的關係 如果 CDN 的快取時間跟你設的 max-age 不一致，先看有沒有 s-maxage——它會覆蓋 max-age，而且只影響共享快取。兩者並存時很容易誤判。
  3. 確認你看的是哪一層快取 瀏覽器、CDN 邊緣節點、反向代理各有各的儲存。回應中的 `Age` 標頭會告訴你這份內容在快取裡待了多久——用它判斷內容是從哪一層來的，比猜測可靠。

小結

`no-cache` 允許儲存、要求驗證；`no-store` 才是禁止儲存。這個命名造成的誤解，一邊讓敏感資料在以為受保護的情況下被寫入磁碟，一邊讓過度保守的設定犧牲掉整個快取層的價值。兩種錯誤的代價不同，但根源是同一個。

而真正決定 CDN 效果的往往不是這些指令本身，是 `Vary` 與 `s-maxage` 這兩個較少被談到的部分。如果您的跨境流量需要靠 CDN 擋下大部分回源，這兩項的設定比節點數量更有影響。
